# Window functions

A window function does a calculation over a window of rows while keeping the original rows visible. With `GROUP BY`, you collapse many rows into one summary per group, like one row per session with a total. A window function computes across multiple rows but does not collapse anything. It adds a new column to each row, so you keep every row, now with a calculated value alongside it.

A common use is ranking. `ROW_NUMBER()`, `RANK()`, and `DENSE_RANK()` number rows in an order you choose, such as events ordered by time. They differ on ties. If two rows are tied for second place, `ROW_NUMBER()` still assigns distinct numbers, giving them 2 and 3. `RANK()` gives both 2, and the next row becomes 4, leaving a gap after the tie. `DENSE_RANK()` gives both 2, and the next becomes 3, with no gap. Many mistakes come from using the wrong one when ties exist. One catch hides inside ROW_NUMBER(). The SQL promises the tied rows the numbers 2 and 3, but it does not promise which row gets which: with nothing in the ORDER BY to separate them, the choice is the engine's, and it can differ between runs. Add a tie-breaker, a unique column such as event_id, and every number becomes fixed. RANK() and DENSE_RANK() dodge the problem by giving tied rows the same number. ROW_NUMBER() cannot.

Another use is running totals. SUM(value) OVER (ORDER BY occurred_at) adds values as you go down the rows, so each row shows a 'so far' total next to it. But 'so far' depends on the frame, the set of rows the sum covers, and SQL's default frame is subtler than it looks. The default is RANGE, which treats rows that tie on the ORDER BY value as one step: both tied rows show the same total, the sum including both of them. The alternative frame, ROWS, counts physical rows one at a time, so tied rows show different totals, in whichever order the engine happens to feed them. One word changes the numbers on exactly the rows where ties live. The frame is part of the meaning, not a detail.

`PARTITION BY` splits the rows into groups and restarts the calculation within each group. `SUM(...) OVER (PARTITION BY session_id ORDER BY occurred_at)` gives each session its own running total instead of one total across the whole table. The same applies to ranking: you can number rows within each session, user, or any grouping key.
