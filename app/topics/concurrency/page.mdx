# Concurrency

The previous topic looked at one transaction running by itself. Real databases do not work that way for long. They serve many users at once, so transactions often run at the same time. That is usually good because it keeps the system responsive. The trouble starts when two transactions touch the same data at the same time. If the database does not control the overlap, they can interfere with each other.

A common problem is the lost-update bug. Imagine two transactions both want to update the same value. Each one reads the current value, changes it, and writes the result back. If they run one after the other, the result is fine. But if they overlap, the second transaction may read the value before the first transaction has saved its change.

Now the second transaction is working from a stale value. When it writes its result back, it overwrites the first transaction's update. One of the updates disappears. There may be no error message, no crash, and no obvious sign that anything went wrong. The database still contains a normal-looking value, but it is the wrong value. Notice what the bug needs: the read and the write are separate steps, with a gap between them. The staleness enters through that gap. Every fix below is a way of closing it.

This kind of bug is dangerous because it depends on timing. Most of the time, the two transactions may not overlap in the exact wrong order, so the code seems correct. Then, under load or bad luck, the timing lines up and the bug appears. That makes it easy to miss in testing and hard to reproduce later. The figure shows one specific ordering chosen to make the bug visible, not something that happens every time.

There are three standard fixes, and the figure runs all of them. The first removes the gap: one UPDATE statement, UPDATE accounts SET balance = balance + 50, reads and writes in a single motion, so whenever it runs it computes from the current value, never a stale one. (If the other transaction holds the row lock, the statement waits for it, as it would in PostgreSQL; what it never does is work from an old read.) The second fix takes the lock early: SELECT ... FOR UPDATE locks the row at the read, so the second transaction waits before it reads, then reads the updated value and applies its change to that. The third is the version check: give the row a version number, and write only if the version is still the one you read. If it has moved, the write matches no rows, the clash is detected instead of silent, and you retry with the fresh value. One statement removes the gap, locking moves the wait to the read, and the version check catches what the others prevent.

Run the overlap in the figure, both transactions reading before either writes, and the modes separate. In read, then write, the second write overwrites the first and one update vanishes: 150 where 200 belongs. Watch it closely: the second write even waits for the row lock, and the update is still lost, because waiting at write time cannot rescue a value computed from a stale read. One UPDATE statement lands on 200, computing from the fresh value whenever its turn comes. SELECT ... FOR UPDATE lands on 200 by holding the second transaction at its read. The version check lands on 200 after one honest retry, and it is the only mode that tells you a clash happened. Run the transactions one after the other instead, with no overlap, and every mode lands on 200: the bug needs the overlap as much as it needs the gap.

This is one specific problem that can happen when transactions overlap. Databases offer different isolation levels that control which of these problems can occur, which is the next topic.

The figure runs the real statements, not a sketch of them: the SQL in each mode is the SQL a database would execute, on balances that are real arithmetic kept small for clarity. What it simplifies is the setting, one row and two transactions, so the interleavings stay countable. In real systems the same statements run at scale, and the overlap that arms the bug is timing-dependent and does not always happen, which is exactly what makes it dangerous.
