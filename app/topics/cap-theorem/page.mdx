# CAP theorem

The Databases section dealt with one node keeping its promises. Run two copies of the data on two nodes, and a new problem appears that no amount of clever code removes: the network between them can fail. The CAP theorem is about the choice that failure forces.

The figure keeps replicas of one value in sync over a network: two nodes by default, or three if you switch the cluster size, which is where the majority rule below comes from. While the link is healthy, life is good: a write to either node crosses the link, both copies agree, every read on either side returns the same answer. Consistency and availability, both at once. The theorem is not about this case, and any framing of CAP as "pick two of three" starts wrong: a partition is not something you pick, it is something the network does to you.

Break the link and the choice arrives. Node A's client wants to write, and node A cannot tell node B. There are exactly two honest responses, and the toggle lets you run the same sequence under each.

Prefer consistency, and the rule is majority: an operation succeeds only on a side holding more than half the nodes, because only that side can be sure the others will agree. Break the link between two nodes and neither side has a majority, so everything is refused: the counter climbs to six while the two values sit untouched and identical. Cut one node off from a three-node cluster and the picture splits: the two-node side serves on, and the lone node refuses, falling behind but never diverging. Nothing on a refusing side ever needs repairing. The price is that part of the system, for the duration, is simply down.

Prefer availability, and the system serves. Every operation succeeds locally, both clients stay happy, and the two replicas quietly become two different truths: x is 2 on one side and 3 on the other. The divergences counter pays the price this time, counting every operation that ran while the nodes disagreed. Then heal the link and meet the bill: the system now holds two values for one key and must reconcile them. How systems resolve such conflicts is a hard topic of its own; this figure stops at the moment the conflict becomes undeniable.

Run the sequence and read the prices. Healthy: nothing. Two nodes, consistent under partition: six refusals. Two nodes, available under partition: six divergences and a conflict to resolve. Three nodes, consistent, one cut off: the majority serves, the lone node refuses three operations and falls behind, then catches up on heal with no conflict, because it never accepted a write. That is the theorem with its working case restored: when the network partitions, you choose which price to pay, and not whether to pay one. A majority is how real systems arrange to pay the smaller one.

Two clarifications the terminology deserves. The C here is stricter than the C in ACID: CAP's consistency means every read sees the latest write as if there were one copy, a statement about replicas, while ACID's consistency is about a single database honoring its own rules. And this figure is still deliberately small: one key, synchronous replication, clusters of two and three. Real systems run more replicas, replicate asynchronously, and offer consistency levels between the two poles shown here. The poles are what the theorem is about; the majority case is how production systems live between them.
