# SQL vs NoSQL modeling

The Normalization topic split one wide table into three, and admitted the cost: joins to reassemble what one row used to show. That trade has another side, and this topic gives it a fair fight. Take the same users, plans, and orders and model them twice: once as normalized relational tables, once as documents, where each user is a self-contained object with its plan details embedded and its orders nested inside.

Neither shape is the right one. Which shape wins depends entirely on what you ask, and the figure lets you ask three things.

The figure prices each operation on its own, in places opened. Fetch everything about one user: the relational side opens 3 places, users, plans and orders, and stitches them together. The document side opens 1, because everything about that user was stored together in the first place. This is the document model's core bet: data that is read together should be stored together.

Change the pro plan's price, and the prices invert. The relational side opens 1 place and changes one cell; there is nothing else to disagree with it. The document side opens 2 places and rewrites 2 copies, because the price is embedded in every pro user's document. This is the update anomaly from the Normalization topic, reintroduced deliberately: embedding is denormalization, it buys the fast fetch above by copying facts, and copies can drift. The panel counts copies written alongside places opened, because a cheap operation that quietly writes the same fact twice is not cheap in the way that matters.

Ask a question across users, all orders over 25: the relational side opens 1 place, the orders table, though opening one place still means reading all 5 order rows inside it; places opened and rows read are different counts, and the honest one depends on the question. The document side opens 3 places, one document per user, digging into each nested array. A real document store can soften this with secondary indexes, which is an engine feature rather than a property of the shape, but the shape itself is fighting the question.

The three prices point in different directions, so no shape wins until you say how often each operation runs. That is what the workload panel is for: three sliders set the mix. At the default mix, 60 percent fetches, 10 percent price changes, 30 percent cross-user queries, the relational side averages 2.20 places opened per operation and the document side 1.70, so documents are cheaper for that workload, and the copies count stays visible beside the score for the workloads where it grows.

The break-even has a clean rule, and the figure's tests check it at every mix: documents win exactly when twice the fetch share is more than the price-change share plus twice the cross-user share. Read it as forces: every point of fetch share pulls toward documents with double weight, because the fetch is where the 3-to-1 gap lives, and every point of cross-user share pulls toward tables with the same double weight. Price changes pull toward tables too, more gently. Slide the mix and watch the winner flip at exactly the line the rule predicts.

The pattern behind all three: the document layout is an answer frozen in storage form. Store the data pre-assembled for one question and that question gets very cheap, while questions that cut across the assembly, or update a fact inside many copies, get awkward. Normalized tables refuse to pre-assemble anything, which keeps every fact in one place and every cross-cutting question reachable, at the price of join work on every read.

So the modeling question is not which technology is better. It is: what will this data be asked, most often, by whom? Read-heavy, self-contained, one-entity-at-a-time access patterns lean toward documents. Shared facts, frequent updates, and cross-entity questions lean relational. Many real systems use both, one as the source of truth and the other as a shaped copy, which is a topic for another day.
