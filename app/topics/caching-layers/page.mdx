# Where caches live: browser to database

The Caching topic showed one cache making decisions: what to keep, what to evict, what a miss costs. Real systems do not run one cache. They run several, stacked between the user and the database, and a read checks the closest one first.

The stack in the figure has four layers. The browser cache lives on the device itself. A CDN holds copies at the network edge, close to users. Redis sits next to the application servers. And at the bottom is the database, the source of truth, which always has the answer and always pays the most to give it.

A read falls through the stack. It checks the browser first, then the CDN, then Redis, and stops at the first layer that has a copy. Only a miss everywhere reaches the database. What happens on the way back depends on which layer answered, and this is where the stack is not one mechanism but two. Browsers and the CDN are HTTP caches: they store responses travelling back from the server, and only when the response's Cache-Control header allows it. Public responses may be stored by any cache, private ones only by the reader's own browser, and no-store ones by nobody. Redis is a different kind of cache, owned by the application rather than the HTTP path: the app fills it after a database read, under its own time-to-live. So a Redis hit puts nothing into the browser or the CDN, because no fresh response travelled the HTTP path for them to store; the app simply answered from its own cache. Two systems, one stack, different rules.

That is why the figure starts cold. Every cache begins empty, so the first reads all fall straight through and the database answers everything. Watch the counters as the stream plays: the database works hard early, then the layers fill with the copies they are each allowed to keep, and later reads stop higher and higher in the stack. Nobody flips a switch from cold to warm. The caches earn it, one permitted copy at a time.

Which layer a copy may live in is a safety question, not just a speed one. Mark a personal response, like /api/me, public and the shared CDN is allowed to keep it, and a shared cache serves whoever asks next: the figure's ugliest moment is the CDN handing one reader's profile to another. That is why real systems mark personal data private or no-store even though caching it would be faster. The header is each layer's permission slip, and getting it wrong does not just miss. It leaks.

Two honesty notes. The read stream is authored for teaching, with a hot key, some medium ones, and a few one-offs, but every outcome you see is computed by running real caches over that stream; nothing is scripted per read. The latency labels on the layers are illustration, typical orders of magnitude, not measurements.
